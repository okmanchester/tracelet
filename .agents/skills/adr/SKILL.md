# 系统架构决策记录

支持提案和追溯，不代表 AI 有权批准架构选择或实施提案。

## 先读项目约定

- [ADR 规范与索引](../../../docs/adr/README.md)：适用范围、证据要求、编号、状态和决定权限的唯一规范；处理 ADR 时先读取。
- [ADR 模板](../../../docs/adr/template.md)：创建或完整性审查时读取，直接复用，不在 skill 内维护副本。
- [系统已知问题](../../../docs/architecture/known-issues.md)：核查关联问题、现有证据和验收条件。

以上链接相对于本 SKILL.md；从任何工作目录调用都按文件所在目录解析。规范或模板不可用时说明缺项，不臆造项目规则或历史决定。

## 工作方式

1. 判断是否存在具有长期系统影响的架构取舍。若只是流程规范、文档管理或普通修复，说明不需要 ADR，沿用普通任务或问题记录；不要额外要求架构审批。开发或部署工作按实际系统影响判断。
2. 阅读相关问题、已有 ADR 及替代链，核查当前代码与原始资料。区分已证实事实、假设、待验证项和未测量内容；当前实现不能证明过去为何选择或曾获批准。没有数据时如实说明。
3. 达到门槛后，为一个具体决策创建 Proposed，或修订同一主题的现有 Proposed。按规范分配不复用的编号，用唯一模板写清背景、可行替代方案、取舍、负面后果、验证与重评条件。已有 Accepted 的实质性变更须新建提案。
4. 检查证据是否可定位、替代方案是否真实、推荐理由是否解释代价、未知项是否明确；不编造性能数字、历史批准或凑数选项。索引及关联问题双向链接，新增 ADR 保持 Proposed。
5. 将完整的具体提案及待决定事项交给用户。用户尚未明确决定时完成可审阅草稿并保留 Proposed，不实施未经授权的架构方案，不替用户接受或否决。已有明确决定覆盖同一具体内容时不重复询问。
6. 只有明确决定才能触发正式状态变化；按规范登记决定人、日期、具体版本和可定位依据。替代新方案获准后再维护旧记录状态与双方链接。保留原决定，实施及验收证据按日期补充，Accepted 不等于问题已解决。

## 交付前检查

核查状态、批准依据、索引、替代链和相对链接一致；没有依据的字段留空。说明起草或更新了哪些记录、哪些仍为 Proposed、有哪些事实尚待验证。普通问题不因本 skill 变成架构决策，也不把文档批准当成实现授权。
