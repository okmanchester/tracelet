# 限流与重试

## QPS 与配额的区别

限流有两个相互独立的维度：

- **QPS（每秒请求数）**：按应用维度计算的秒级上限，控制瞬时并发。超出返回 HTTP 429 `RATE_LIMIT_EXCEEDED`。
- **月配额**：每个计费周期（自然月）内的调用总量上限。超出返回 HTTP 429 `QUOTA_EXCEEDED`，或按套餐规则转为超额计费，具体以套餐说明为准。

QPS 超限是短时问题，通常退避后即可恢复；配额耗尽需要升级套餐或购买加量包，次月自动恢复。

各套餐的 QPS 与月配额：

| 套餐 | QPS | 月配额 |
| --- | --- | --- |
| 免费版 | 5 | 10,000 |
| 基础版 | 20 | 100,000 |
| 专业版 | 50 | 500,000 |
| 企业版 | 200 | 2,000,000 |

## 429 的处理方式

收到 429 时先看响应中的 `code`：

| 错误码 | 含义 | 处理方式 |
| --- | --- | --- |
| `RATE_LIMIT_EXCEEDED` | 瞬时 QPS 超限 | 本地限速 + 指数退避重试 + 错峰调用 |
| `QUOTA_EXCEEDED` | 月配额耗尽 | 查看用量，升级套餐或购买加量包，不要盲目重试 |

无论哪种情况都**不要立即高频重试**，否则会进一步压低成功率和拖慢恢复。

## 指数退避重试

推荐策略：

1. 仅对可重试错误重试：HTTP 429、5xx、网络超时。
2. 初始退避 1 秒，每次乘以 2，设置最大退避上限（如 30 秒）。
3. 加入随机抖动（jitter），避免大量客户端同时重试造成新的尖峰。
4. 设置最大重试次数（如 3~5 次），超过后记录 `request_id` 并告警。
5. 对 4xx 参数错误、401 鉴权错误不要重试，应先修正配置或参数。

Python 参考实现：

```python
import random
import time


def backoff(attempt: int, base: float = 1.0, cap: float = 30.0) -> float:
    delay = min(cap, base * (2 ** attempt))
    return delay * (0.5 + random.random() * 0.5)


for attempt in range(5):
    resp = call_api()
    if resp.status_code != 429 and resp.status_code < 500:
        break
    time.sleep(backoff(attempt))
```

## 主动限速

- 在客户端实现令牌桶或信号量，把并发控制在套餐 QPS 的 80% 左右，预留突发余量。
- 批量核验类任务建议排队串行消费，不要一次性打满并发。
- 多实例部署时使用共享限速器（如 Redis 令牌桶），避免各实例独立限速导致总量超限。

## 如何判断是限流还是平台故障

按以下顺序排查：

1. 查看响应状态码与 `error_code`：429 且带 `RATE_LIMIT_EXCEEDED` 表示限流，不是故障。
2. 检查是否集中在该租户或该应用：只有自己的流量出现 429，通常是自身并发过高。
3. 观察时间分布：突发流量、定时任务、重试风暴都会造成短时集中 429。
4. 若出现大面积 5xx、超时或所有租户同时异常，可能为平台故障，记录 `request_id` 并联系技术支持。
5. 对比调用日志中的延迟与成功率，限流场景通常延迟正常、仅状态码为 429。

## 常见问题

**升级套餐后为什么仍然 429？** 确认是否属于配额耗尽（`QUOTA_EXCEEDED`），以及套餐变更是否已生效；同时检查客户端并发是否仍超过新的 QPS 上限。

**重试越多成功率越低？** 说明已经进入重试风暴，应立即停止无上限重试，加入退避与抖动，并降低并发。

**可以申请临时提高 QPS 吗？** 可通过工单联系技术支持说明业务场景与预估峰值，由商务与平台团队评估。
