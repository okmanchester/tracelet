## 背景与问题

前两批已将安全初始化、显式重置和演示装载分开，并提供独立的 MySQL 验收入口。但 `create_all` 只创建缺失表，不能为已有表增加或修改字段，数据库也没有受管理的 schema 版本。继续修改 ORM 模型会使新库与存量库走向不同结构。

需要确定迁移历史的来源、已有数据库如何进入版本管理，以及迁移失败时能作出的保证。这会影响此后的全部 MySQL schema 演进，因此作为一个具体系统架构选择记录。该提案不改变业务字段、金额类型、权限规则或知识库发布机制。

## 决策驱动因素

- 默认初始化和升级必须保留现有业务数据；结构不明时拒绝写入，不能自动删表修复。
- 历史迁移须能独立复现，不能因将来修改 ORM 而改变最初版本的含义。
- 存量库必须先核对结构，再明确登记版本，不能把登记版本等同于已执行变更。
- 沿用现有 SQLAlchemy、同步连接和隔离测试入口，控制本批范围。

## 替代方案与取舍

| 方案 | 如何解决问题 | 优点 | 成本、限制与风险 | 与驱动因素的关系 |
| --- | --- | --- | --- | --- |
| 保持 create_all，人工执行 ALTER | 文档维护每次差异并手工改库 | 无新增依赖 | 无可靠的版本历史、执行顺序和一致性检查，人工遗漏仍可能发生 | 不能满足受管理演进和可重复验证 |
| 自建 SQL 迁移账本与执行器 | 固定 SQL 文件、版本表和顺序执行 | 可直接审阅 MySQL SQL | 自行维护版本图、状态检查、工具接口及测试，长期维护面更大 | 可行，但对当前 SQLAlchemy 项目收益不足 |
| Alembic 固定迁移历史，校验后显式接管 | 初始迁移建库，后续 revision 演进；旧库通过检查后 stamp 初始版本 | 复用成熟迁移工具及现有 ORM 信息，历史可审阅 | 新增依赖、迁移文件和严格接管逻辑；MySQL DDL 仍不具备整批原子性 | 推荐，兼顾可追溯性和本批规模 |

不推荐未检查就 `stamp head`，也不推荐通过自动重建或自动修复差异来接管存量库；这些做法不能证明结构相符或数据得以保留。

## 已决定方案

以下方案已由用户于 2026-10-19 明确接受；具体实现进度与验收结果见关联问题，Accepted 不表示已经通过验收。

### 固定迁移历史

- 使用 Alembic 管理业务 MySQL schema，版本表使用 `alembic_version`；复用现有同步 SQLAlchemy 连接，不在迁移配置中保存凭证。
- 第一条 revision 为 `0001_initial_schema`，冻结本次检查的 19 张表、列、索引及外键定义，保留 `DATETIME(6)` 等现有类型；只建立基线，不夹带业务字段调整。
- 初始 revision 使用显式、可审阅的 DDL 操作，不调用当前 ORM 的 `create_all`。未来变更新增 revision，不重写已经应用的基线。
- 自动生成仅用于生成候选变更，必须审阅。初始版本不提供普通业务入口执行降级；破坏性重置仍走单独确认入口。

### 初始化、升级与存量接管

- 提供 `python -m scripts.migrate_db current`、`check`、`upgrade`、`adopt-baseline --yes`。`current`、`check` 只查询；`upgrade` 的目标固定为本仓库的唯一 head。
- 空库通过 `upgrade` 执行完整迁移历史。已登记且版本已知的库沿版本链升级；重复升级至 head 不重建表或修改业务记录。
- 非空、未登记的库必须拒绝普通升级，并提示执行接管检查；不得自动 stamp、补表、删表或改列。
- 接管只针对冻结的 `0001_initial_schema`，不针对随未来代码变化的 ORM/head。仅在无版本且完整匹配基线时，显式确认后登记基线；同一匹配基线再次接管可作为无写入的成功操作。未知、多分支或较新版本拒绝接管和升级。
- 接管核查表和列集合、类型及长度/精度（包含时间微秒精度）、nullable、服务端默认值、主键、唯一约束/索引及外键；自动命名差异按结构语义比较，必须验证 MySQL Boolean/TINYINT、唯一索引等反射差异。额外或缺失的表、列、约束及不兼容类型均拒绝，不能忽略差异后 stamp。
- Alembic 的差异比较是校验的一部分，不能宣称它覆盖全部 MySQL 对象。触发器、存储过程等未由当前 ORM 描述的对象及权限可见性须在存量库接管检查中说明；超出可验证范围的库交人工评审，不承诺自动兼容。
- `init-db`/`setup` 的 MySQL 部分改为调用受控升级，再确保 Milvus 集合存在。已有未登记库首次运行会被安全拒绝，需要先显式接管；这一兼容变化须写入使用说明。
- `reset-db CONFIRM_RESET=1` 和 `init_db --recreate --yes` 保留明确确认，删除受管业务表及版本表后，通过迁移历史重建 MySQL，再按现有规则重建 Milvus。不能留下旧版本表而让升级错误地跳过建表；不自动种子装载或清理 Redis。

### 执行与失败边界

- 迁移只由显式初始化或管理命令执行，不放在应用启动钩子中。部署/接管期间不并行执行其他 schema 变更，存量接管前保留可恢复备份。
- 写命令在同一连接上取得按数据库名区分的 MySQL advisory lock，零等待竞争失败即退出；检查、迁移或 stamp 通过 `Config.attributes['connection']` 复用该连接，最终释放锁。该锁只协调遵守本入口的管理操作，不阻止绕过入口的外部 DDL。
- 结构检查失败不写版本、不执行业务 DDL。MySQL 迁移中途失败则返回非零，不自动重试、不谎报回滚或 stamp 成功；保留错误与当前版本供人工核查实际 DDL 后恢复。
- 普通入口不暴露任意版本 stamp 或破坏性 downgrade。迁移文件和数据库凭证分别管理，错误输出不包含完整连接凭证。

## 后果

### 正面后果

- 新库和已有版本库具有明确、可重复的 schema 演进路径，避免将 create_all 误当作升级机制。
- 旧库接管与实际迁移明确分开，结构未知时保持拒绝写入。
- 基线、后续变更和验收证据可以分别追溯；这些是方案目标，目前尚未实现或测量。

### 负面后果与接受的取舍

- 新增 Alembic 依赖、迁移历史和 MySQL 反射归一化检查，需要持续维护和回归验证。
- 已有未登记的库不再能直接执行新版 setup；须先在备份或副本上检查并显式接管。
- MySQL DDL 失败可能留下部分已生效变更，不能用 Python 事务包装来消除；恢复需要人工核查或从备份恢复。
- 严格接管可能拒绝实际上可用的定制库，处理成本高于自动忽略差异；本批接受拒绝而非猜测兼容。

### 缓解措施与遗留问题

将接管差异列出为可定位但不含凭证的诊断信息，保留备份/副本演练流程，并在真实 MySQL 测试中验证类型和索引反射。Milvus 发布版本、业务并发、金额类型及其他已知问题均不在本批修改。Docker 验收可用性仍是外部执行前提，不通过关闭测试或替换真实库验证来绕过。

## 验证与重新评估条件

接受提案后的实施验收应包括：

1. 空白一次性 MySQL 库执行到 head，19 张业务表及版本正确；结构与现有模型一致，重复初始化/升级保持完整业务记录及关联。
2. 用旧 create_all 建立基线及合成记录，无确认的接管不写入；确认并校验成功后仅登记版本，数据及关联不变。
3. 缺表、缺列、额外表/列、类型或微秒精度、主键/唯一约束/外键不符以及未知版本均拒绝，确认没有错误写入版本或修改业务结构。
4. 在临时迁移目录加入仅供测试的第二条增量 revision，对已有记录执行新增 nullable 列，验证数据保留与版本前进；不向生产基线夹带演示字段。
5. 通过仅供测试的中途失败 revision 观察非零结果、未错误前进的版本及可能残留的 DDL，不能断言事务会恢复所有结构。
6. 验证并发管理命令互斥、失败释放锁、显式重置清理版本并重建，以及缺少确认时无存储操作。
7. 扩展现有隔离验收镜像和构建白名单以包含迁移配置及历史，完整套件必须零失败、零错误、零跳过，并成功清理本次测试资源。

在更换数据库、需要在线零停机变更、多分支迁移或大量定制 schema 时重新评估；这些能力不由本提案默认承诺。真实库迁移测试和完整隔离验收通过前，ARCH-008 不标记 Resolved。
