## 背景与问题

当前最终回复脱敏不能覆盖此前已保存、缓存或提交给模型的原文，若干编排分支也绕过最终安全节点。用户已选择试用阶段不保留敏感原文，同时保留诊断必需业务 ID。本提案定义这一数据边界，不引入受限原文库或可逆还原。

## 决策驱动因素

- 用户误发的凭证和已定义个人敏感信息不进入长期存储、缓存、模型载荷或展示。
- 模型响应、工具结果及异常同样视为可能包含敏感信息，不能只处理用户输入。
- 保留已授权的业务定位能力；不通过保留原文映射恢复敏感值。

## 替代方案与取舍

| 方案 | 如何解决问题 | 优点 | 成本、限制与风险 | 与驱动因素的关系 |
| --- | --- | --- | --- | --- |
| 仅处理最终输出 | 统一回复安全节点 | 改动较小 | 无法保护此前的模型请求、数据库、缓存和日志 | 不满足边界 |
| 加密保留受限原文 | 独立原文存储、密钥与审计 | 人工可复核完整证据 | 需要访问控制、保留期限和删除机制；敏感数据仍被保留 | 不符合用户选择 |
| 入口脱敏并在模型、持久化和展示边界复核 | 共享文本和结构化清洗能力，覆盖所有出口 | 不保留可恢复原文，分支可逐一验证 | 可能误判或损失诊断细节，需要持续维护识别规则 | 已选 |

## 已决定方案

已决定在独立、全新的试用环境实施以下处理，不自动清洗旧库，不新增原文存储：

| 边界 | 允许内容与处理 |
| --- | --- |
| 客户/人工自由文本入口 | 校验权限后、首次写入与调用编排前脱敏；不将原文复制到 meta、异常或后台任务 |
| 会话、缓存与工单 | 消息、历史、实体中的自由文本、查询缓存、摘要、证据和诊断递归处理后保存；不存原文映射 |
| 模型调用 | 在统一模型门面调用 provider 前处理消息和工具上下文、embedding 文本、rerank 的查询和文档；流式调用也使用安全输入 |
| 模型响应和工具返回 | 作为不可信内容清洗后再记忆、记录、汇总或展示；工具参数不能绕过身份校验 |
| Trace、工具日志和错误 | 文本/结构化内容先清洗再截断和序列化；日志和用户错误不包含原始异常载荷或凭证 |
| 最终响应 | 所有编排分支在完整拼接后统一清洗 answer、card、引用及提示；人工回复和推荐回复同样处理 |

- 首批识别范围包括 API Key、显式 Secret、Bearer Token、手机号、邮箱、身份证、银行卡和完整签名。修复短密钥遮盖保留过多字符的问题；短凭证完全替换，长凭证如保留定位片段也不得保留完整值；重复处理结果稳定。
- `request_id`、`app_id`、`api_key_id`、工单/会话/消息/Trace ID、错误码等由服务端验证与授权的结构化定位字段可保留。仅限按调用点列明的字段与允许格式，不因对象中出现同名键就跳过脱敏，也不对白名单字段中的自由文本或凭证放行。自由文本出现凭证时仍遮盖。
- 统一模型门面作为外发复核点，业务存储和最终展示边界分别防御；不能以门面处理替代首次落库前脱敏，也不能以正则代替现有内容安全审核。
- 最终出口在工单提示等文本拼接之后执行，覆盖缓存、澄清、异常兜底和建单失败；保持成功响应结构不变。响应 ID 与关联信息按上述授权规则保留。
- 脱敏失败时返回固定、无敏感细节的错误并停止当前外发/写入；不降级成原文透传，不通过日志打印原始输入排错。
- 现有生产路径仍先审核完整答案再分块返回。本批不引入未经审核的模型 token 实时展示；未来增加该能力需重新评估增量审核方式。

## 后果

### 正面后果

可逐边界验证敏感标记不进入存储、外发与展示；原文不会通过新建的还原映射继续保留。以上保留提案形成时的目标；批准后的实施与验收记录见文末和关联问题。

### 负面后果与接受的取舍

脱敏不可逆，会丢失人工排障细节；规则存在漏报和误报，需要维护。多个边界处理增加 CPU 与维护成本，未测量耗时；规则升级后旧缓存或旧内容不能自动视为合规。

### 缓解措施与遗留问题

使用合成凭证和业务 ID 反例、幂等测试及边界拦截断言。试用不复用旧数据；已存在的敏感内容清理如有需求另行规划。保留业务 ID 不代表豁免资源授权，按 [ADR-0002](0002-conversation-ticket-access.md) 执行。缓存重建、业务结果恢复和完整取消契约仍由对应后续批次处理。

## 验证与重新评估条件

1. 用虚构敏感标记检查真实隔离 MySQL 中的消息、工单、Trace、工具/审计日志；Redis 和模型边界先使用可检查参数的替身，不将替身结果描述为真实服务验收。
2. 覆盖正常、澄清、缓存命中、部分/全部 Agent 失败、建单成功/失败、人工补充/回复和推荐话术；检查异常和结构化嵌套数据。
3. 验证 chat/chat_stream、embedding 文档与查询、rerank 均不向 provider 透传敏感标记；清洗失败不外发、不写入。
4. 覆盖短凭证、相邻中文、跨多层结构、重复脱敏、错误消息和原样保留的合法业务 ID；伪装成业务 ID 的敏感值不应放行。
5. 完整隔离回归零失败、零错误、零跳过；第二/三批后再执行真实 Redis、Milvus、模型服务链路的合成数据验收。

引入新敏感类型、外部渠道、文件附件、原文证据需求、遥测出口或模型实时流式展示时重新评估；真实检测能力须以记录方法的实验为依据。
