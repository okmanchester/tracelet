## 背景与问题

重试不能区分“业务没有执行”与“已经提交但结果未返回”。当前工具日志异常会重放业务，聊天首轮重试会创建新会话，反馈拥有另一条建单路径。需要统一持久化操作身份、提交结果和恢复查询。

## 决策驱动因素

业务事实、幂等结果必须一起提交；身份来自认证上下文；初始会话也要可恢复；复用现有 MySQL 和迁移机制，避免依赖 Redis 存活保证写入唯一。

## 替代方案与取舍

| 方案 | 如何解决问题 | 优点 | 成本、限制与风险 | 与驱动因素的关系 |
| --- | --- | --- | --- | --- |
| 禁止自动重试 | 缩小重复执行机会 | 改动小 | 客户重复提交、提交后断连仍会重复建单 | 仅适合作为临时限制 |
| Redis 幂等锁与结果缓存 | 按请求键互斥并缓存结果 | 访问快 | 过期、重启及与 MySQL 跨存储提交仍有不确定窗口 | 无法独立提供持久化保证 |

## 已决定方案

### 请求身份与兼容边界

- 聊天及反馈请求增加必填 UUID `request_id`；前端在一次用户操作开始时创建，网络重试、结果查询和页面恢复使用原标识。用户修改内容后才创建新标识。
- 幂等范围为认证的 `tenant_id + user_id + operation_type + request_id`，数据库唯一约束兜底。操作类型至少区分 chat、feedback、create_ticket；模型参数不能指定或覆盖这些字段。
- 操作记录保存规范化、脱敏后请求的摘要、目标会话、状态、业务结果关联和时间。摘要包含目标会话、正文或反馈类型及关联消息；不保存原始敏感内容。UUID 原文只允许规范 UUID，不接收任意自由文本。
- 相同范围及标识但请求摘要不同返回 409；相同请求查询已有结果。授权在结果读取前重新检查，不向其他身份返回操作存在性或内容。
- 前后端协调发布；缺失或非法 request_id 返回 422，不悄悄生成一次性标识。本项目现有调用方和测试随接口调整，不宣称对旧客户端透明兼容。

### 提交与恢复

- 新增操作表；聊天接收事务同时保存操作、首次会话和用户消息，避免首轮响应丢失后新建会话。后续处理按原操作恢复，不重复保存用户消息。
- 内部区分 processing、succeeded、failed、unknown；failed 只表示已确定未提交的执行失败。数据库不可达或提交结果不明时对外报告 unknown，不将异常等同于回滚成功。
- 新增 `GET /api/operations/{operation_type}/{request_id}`，只返回本认证身份有权读取的操作状态、会话和已提交结果；不存在或不可见统一 404。processing、unknown 不被前端展示为成功。
- 建单服务接收调用方事务，不自行 commit。反馈与 Agent 建单共用该服务；操作结果与工单同事务提交，人工模式切换同时提交，见 ADR-0005。
- Agent 执行阶段仅形成待建单意图；最终提交时创建工单。服务端从父操作派生稳定的建单子操作标识，每个父操作至多一个建单动作；通过 ToolContext 传递，不能由模型生成或替换。
- 提交异常后丢弃原会话连接，用新连接按原操作查询。数据库仍不可达时返回可重试的未知状态；客户端保持原 request_id。恢复后查询持久化记录，再判断是否允许继续。
- 成功操作结果保留，不按短缓存 TTL 删除。试用阶段不提供自动清理；未来如需保留期必须同时定义重复请求失效契约。

### 工具重试

- 工具声明只读或写入属性。只读操作可按现有预算重试；无持久化幂等支持的写操作禁止自动重试。
- 日志独立于业务重试块；日志失败不能重放工具或覆盖已提交业务结果。记录固定错误和操作关联，不记录敏感原文。
- 幂等写操作只能复用原子操作标识；不因超时生成新工单。已知成功结果直接返回，不再次执行模型或写工具。

## 后果

### 正面后果

重复请求和提交后响应丢失可以关联同一结果；不再依赖“客户端不会重发”或工具日志可用性。这些是方案目标，尚未实施验收。

### 负面后果与接受的取舍

增加操作表、索引、结果保留成本和客户端协议变化。稳定请求标识不能自动判断用户用两个新标识表达的诉求是否相同。本方案不保证外部模型只调用一次，也不为未来外部支付等服务提供跨系统恰好一次语义。

### 缓解措施与遗留问题

按身份限权查询、数据库唯一约束、提交故障注入及同库事务验证；后续新写工具必须声明重试策略。处理中占用与异常执行恢复依赖 [ADR-0007](0007-conversation-execution-fencing.md)，附属写入补偿见 [ADR-0006](0006-conversation-source-and-recovery.md)。

## 验证与重新评估条件

1. 同请求串行及并发重复、日志异常、首次会话响应丢失均仅产生一份业务记录。
2. 模拟 commit 已执行但抛连接异常，以新连接查询同一工单；真实数据库不可达时不能宣称成功或产生新操作。
3. 请求内容冲突为 409；缺标识为 422；跨身份查询拒绝，且不发生模型或业务写入。
4. 建单和操作结果的事务分别注入提交前失败、提交后异常；结果与业务记录不能分离。
5. 后续启用外部写操作、自动清理操作历史或多区域写入时重新评估。
