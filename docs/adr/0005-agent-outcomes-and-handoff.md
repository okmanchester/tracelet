## 背景与问题

当前 Agent 的布尔字段由 Supervisor 分散解释，文案、工单和会话模式可以互相矛盾。需要显式区分生成结论、请求业务动作及动作提交结果，由一个决策入口生成最终可展示状态。

## 可验证事实与不确定项

| 事实或判断 | 证据类型 | 来源与定位 |
| --- | --- | --- |
| 诊断、账单和 RAG 各自定义结果，通过 getattr 汇总 | 源码确认 | [api_diagnostic.py](../../backend/app/agents/api_diagnostic.py)：`DiagResult`；[billing.py](../../backend/app/agents/billing.py)：`BillingResult`；[doc_rag.py](../../backend/app/agents/doc_rag.py)：`RagResult` |

| 客户反馈直接建单并设置人工模式 | 源码确认 | [tickets.py](../../backend/app/api/tickets.py)：`submit_feedback` |

| 专业 Agent 的真实失败率和人工处理容量未知 | 未测量 | 不据此设置失败率阈值或人工响应时限 |

## 决策驱动因素

回复与持久化事实一致；模型只产生建议，不决定写入成功；保留有效部分结果；建单、转人工可以分别表达；所有分支继续执行已接受的权限与脱敏规则。

## 替代方案与取舍

| 方案 | 如何解决问题 | 优点 | 成本、限制与风险 | 与驱动因素的关系 |
| --- | --- | --- | --- | --- |
| 逐分支修补布尔值与文案 | 保持现有结构并补判断 | 局部改动少 | 新 Agent 继续隐含解释，提交事实与生成文案容易分离 | 不适合作为长期契约 |
| 所有建单都转人工 | 合并两个业务动作 | 状态较少 | 不满足诊断建单后继续 AI 的选择 | 不推荐 |
| 统一结果契约与集中决策 | 先收集结果，再确定业务动作，提交后生成动作状态 | 语义可测且独立于 Agent 实现 | 需要调整全部生产者及展示逻辑 | 推荐 |

## 已决定方案

- 引入统一 AgentOutcome：状态为 answered、no_hit、insufficient、failed；携带 answer、card、citations、evidence、tokens，以及建单或人工需求和固定原因码。不得以缺少 card 推断失败，不得使用异常原文作为客户回复。
- Supervisor 收集显式类型，纯决策函数输出回答/澄清与待执行业务动作；Agent 不自行完成最终建单或切换模式。兼容原内部结果时集中在适配器，不继续逐节点使用 getattr 猜测。
- 建单动作只在最终事务执行；前端动作状态及固定确认文案在提交后确定，不能由模型提前宣称。模型关于“已建单/已转接”的承诺不作为动作事实，最终出口以服务端确认信息为准。

| 场景 | 默认动作与回复 |
| --- | --- |
| 有可用结果，包括部分 Agent 技术失败 | 展示有证据的结果；说明未完成部分，不因局部失败自动接管 |
| 文档无命中 | 保留无命中解释和人工入口；不建单、不切换模式 |
| 信息不足 | 明确所缺信息并澄清；如诊断明确建议跟进，可建单但继续 AI |
| 诊断需要工单跟进 | 建单成功返回工单号；AI 模式不变 |
| 用户明确请求人工、需人工的受限业务 | 尝试建单与切换模式；成功后确认已转人工 |
| 全部选中专业 Agent 技术失败、管线技术故障 | 尝试建单转人工；不将故障误作无命中 |
| 建单失败且确定未提交 | 明确动作未完成，保持原模式；原操作保存可重试状态 |
| 提交结果未知 | 不声称成功或失败；按原操作查询，不另建单 |

- 重复人工反馈复用其原请求结果；对已经处于人工模式的会话，新的“转人工”请求返回当前模式和已关联的有效接管工单，不重复创建接管工单。普通独立诊断工单仍按各自操作区分。
- 建单、操作结果及人工模式切换使用同一数据库事务。工作台主动接管不要求先建单，但必须使在途 AI 失去提交资格，见 ADR-0007。
- 完成结果继续提供 answer、card、citations、ticket_id、need_human 等既有 SSE 字段；need_human 只表示实际已提交的人工模式。增加 request_id、operation_status、ticket_status、handoff_status 区分意图与事实。
- 最终动作错误采用固定脱敏文案，不输出 `工单号 None`，不承诺人工响应时间。所有分支继续经过统一安全出口。

## 后果

### 正面后果

无命中解释可以保留，业务动作可测试，前端可以依据已提交事实展示状态。上述能力尚待实施与验收。

### 负面后果与接受的取舍

所有 Agent 结果与测试替身需要迁移，前端需适配更多显式状态；失败重试必须保留原操作，不能简单整轮重跑。自动失败建单会增加人工负担，实际规模未测量。

### 缓解措施与遗留问题

使用纯决策矩阵测试，业务事务使用真实隔离 MySQL；成功文案由服务端确定。模型答案质量、知识发布和人工排班不属于本决策。

## 验证与重新评估条件

覆盖矩阵每一行及组合场景；断言客户文案、工单数量、操作结果与会话模式一致。建单失败、重复反馈及提交未知必须有固定行为；无 card 的无命中解释不得丢失。缓存仅保存无需业务动作且合适复用的文档答案，不能重放接管动作。人工恢复 AI、更多业务写动作或新的接管渠道启用时重新评估。
