## 背景与问题

消息落在 MySQL，编排却依赖有 TTL 的 Redis 历史。人工及直接追加消息不进入该投影；图执行后的附属写入异常还能阻止答案返回。需要明确事实来源、上下文版本与可恢复的附属工作。

## 可验证事实与不确定项

| 事实或判断 | 证据类型 | 来源与定位 |
| --- | --- | --- |
| Redis 历史窗口为 20 条，历史和实体均有 6 小时 TTL | 源码确认 | [session.py](../../backend/app/memory/session.py)：`HISTORY_MAX`、`ENTITY_TTL`、历史与实体接口 |
| 图前读取 Redis，图后顺序写记忆、Trace、成本和缓存 | 源码确认 | [supervisor.py](../../backend/app/agents/supervisor.py)：`load_context`、`intent_node`、`run` |
| SQL 已有消息及会话 collected_entities，人工消息仅写 SQL | 源码确认 | [models.py](../../backend/app/models.py)：`Message`、`Conversation`；[workbench.py](../../backend/app/api/workbench.py)：`human_reply` |
| 真实 Redis 故障和跨 worker 恢复未验收 | 待验证 | 后续隔离 Redis 场景与准入阶段真实依赖演练；没有性能数据 |

## 决策驱动因素

已提交的客户、AI、人工消息应具有同一事实来源；上下文不得因 Redis 过期丢失；附属故障既不影响业务成功，也不静默丢弃；继续仅保留脱敏内容。

## 替代方案与取舍

| 方案 | 如何解决问题 | 优点 | 成本、限制与风险 | 与驱动因素的关系 |
| --- | --- | --- | --- | --- |
| 延长 Redis TTL、逐入口双写 | 减少短期失效并补人工消息 | 改动较少 | 双写仍可能分离，Redis 故障继续影响上下文 | 不推荐作为事实保证 |
| 全部上下文直接读 SQL，附属工作尽力执行 | 去除缓存依赖 | 结构简单 | 没有持久化补偿时会丢失附属记录 | 可作基础，但恢复不足 |
| SQL 事实与版本投影，事务性附属任务 | SQL 提供恢复，Redis 只缓存匹配版本的投影 | 保留缓存且能恢复 | 增加投影版本、任务表和重试运维 | 推荐 |

## 已决定方案

- MySQL Message、Conversation.collected_entities 与会话上下文版本构成事实来源。所有入口通过共享消息服务追加；安全处理在保存前执行。人工回复保留 by=human 元数据，后续模型历史仍按 assistant 角色读取。
- 以会话内递增消息序号稳定排序，不依赖创建时间相同情况下的随机 ID；旧消息在迁移中按 created_at、id 确定性排序回填，此举不能恢复历史上未记录的真实先后。
- 上下文仍取最近 20 条允许使用的已提交消息。本轮客户消息由接收事务保存，但不在本轮 history 中重复出现；加载时按本轮消息序号截断，当前 query 单独传入。
- 本轮实体提取只修改执行内存；通过最终提交资格检查后，才与助手消息、操作结果和版本一起落库。被接管或已过期执行的实体不能污染下轮。
- Redis 投影同时保存消息和实体及 context_version。每轮先读取 SQL 版本，只有完全匹配的投影才能使用；缺失、过期、解析错误或连接故障从 SQL 重建。旧的独立 mem:hist/mem:ent 不作为新版事实读取。
- 不复用旧开发库的 Redis；试用使用新依赖。部署时更换投影键前缀，SQL 事实不受旧键影响。重建失败可记录任务，下轮仍能直接查询 SQL。
- 新增事务性附属任务表；保存已经脱敏的 Trace、成本和必要缓存信息，与业务结果在最终事务一起提交，业务响应不等待其外部执行。任务按操作和任务类型设唯一约束。
- worker 周期处理待办，数据库短事务领取并设置租期，执行失败保存固定原因、重试次数及下次时间。默认指数退避 1、2、4 秒起、最多间隔 60 秒，10 次失败后置待人工重试；提供按操作查询及受控重试命令。服务重启可恢复未完成任务，不引入新的消息中间件。
- Trace 与成本消费者以操作/任务身份去重，同库记录和任务完成一起提交；缓存采用幂等覆盖，写入时仅接受相应上下文版本。重复处理任务不能重复累计成本。
- MySQL 不可用时不能把未保存结果报告为业务成功；依照 ADR-0004 查询或报告 unknown。事务性任务入库失败属于业务提交失败，不伪装为已完成。

## 后果

### 正面后果

Redis 丢失不等于会话丢失；人工消息自然进入上下文；业务成功与可恢复附属任务有同一提交边界。此为目标，尚无新实现验收证据。

### 负面后果与接受的取舍

每轮至少有 SQL 版本检查，增加数据库读取；新增消息序号迁移、任务积压和 worker 运维成本。任务可见延迟使成本/Trace 看板不再与答案同步完成；模型已调用但进程在提交前崩溃时的精确外部用量不能由本方案还原。

### 缓解措施与遗留问题

提供待办、重试、最终失败计数和按操作查询，避免吞掉异常；上线前验证旧数据回填和新键隔离。上下文摘要、无限历史及财务计费准确性不在本决策范围。对话并发及失效执行由 ADR-0007 处理。

## 验证与重新评估条件

1. 清空/过期/损坏 Redis 投影及连接故障后，恢复同一允许窗口；人工和客户追加消息可用，当前 query 不重复。
2. Trace、成本、缓存分别故障时，答案已提交且可查询，任务仍存在；重启消费者后可恢复。
3. 任务重复领取及写入后响应丢失不重复累计成本、不覆盖更新版本；失败 10 次可查询和手工重试。
4. 数据库提交失败不得返回成功；脱敏合成标记覆盖事实、任务及重建出口。
5. 消息序号和版本迁移在独立 MySQL 验证；Redis 原子投影条件通过独立 Redis 验证。
6. 数据库读取成本、任务积压或上下文长度成为瓶颈时，用实测结果重新评估，不预设吞吐提升。
