## 背景与问题

当前知识重建会破坏旧集合，文档展示、进程内 BM25 和 Redis 答案缓存也没有共同的发布边界。已有试用路线用停服备份和恢复限制风险，但下一阶段要求在线切换、单轮版本一致和历史引用可追溯。选择知识事实来源、跨存储发布边界和请求固定版本属于长期一致性及公共契约选择。

本提案扩展知识与缓存版本，不替代 ADR-0004 的操作身份、ADR-0006 的会话事实/附属任务或 ADR-0007 的提交资格。知识发布不取消在途 AI，也不改变人工接管优先级。

## 决策驱动因素

失败构建不能损坏当前版本；发布要有单一可查询结果；在途请求、原 UUID 恢复和延迟任务必须沿用同版。文档和引用不能读取构建后的源文件冒充历史。复用现有 MySQL/Redis/Milvus，继续仅存储与外发脱敏内容。

## 替代方案与取舍

| 方案 | 如何解决问题 | 优点 | 成本、限制与风险 | 与驱动因素的关系 |
| --- | --- | --- | --- | --- |
| 维持维护窗口与快照恢复 | 停服重建，失败恢复旧集合，全部 worker 重启 | 操作和实现改动较小，已有限定范围演练 | 有停机窗口；缺少运行时版本固定和历史引用事实 | 可继续作临时限制，不满足在线切换目标 |
| Milvus 别名作为生效入口 | 新集合验证后切换别名，其他存储配合更新 | 向量侧切换入口集中 | 别名与 SQL 文档、Redis、任务不能同事务切换；在途请求再次用别名可能跨版，仍须增加版本协调 | 可实现向量切换，但不能单独成为本系统发布事实 |

## 已决定方案

### 版本事实与状态

- 服务端产生不可变的 32 位十六进制版本 ID；外部统一称 `knowledge_version`。每版独占集合名，不使用当前别名解析一次轮次中的向量查询。
- 新增版本记录、按版本隔离的文档/切片快照、唯一生效指针及发布记录。现有 KnowledgeDocument 不承担新版本历史主键；通过增量迁移引入新结构，保留旧表和历史。
- 文档保存原公开 doc_id、标题、分类、脱敏正文及内容摘要；现有文件名前缀是公开 doc_id，空值或同版重复拒绝。切片保存文档 ID、顺序、章节、正文、错误码和摘要；chunk_id 由 doc_id、切片顺序及正文摘要确定，在该版检索、快照与引用中保持一致。融合按文档/切片身份去重，不因正文相同混淆来源。
- 版本清单包含文档/切片摘要与数量、切片器配置、embedding 标识/维度/query-prefix 和集合结构。当前 embedding 指纹不作为工件内容完全相同的证明；本地模型须记录可核对的工件摘要，外部模型不可验证的服务端修订明确标记。首批不提供模型迁移或跨 embedding 配置透明回退。
- 构建先快照全部脱敏源文件，再从快照生成切片/向量，不在长构建中反复读取可变源文件。保存状态为 building、built、ready 或 failed；built 后内容不可改，validate 通过才成为 ready；重建使用新版本 ID。
- 是否曾发布由发布记录决定，当前生效由指针决定，不把“历史已发布”和“当前 active”混入构建状态。首批保留所有曾发布快照与集合；failed 构建的显式清理须证明其从未发布、未被操作/任务引用、不是当前指针，并只处理该版资源。

### 构建、校验与发布事务

- `build` 只写本版快照和独立集合；失败记录固定原因，当前版本不变。空文档清单、空切片总量、非法维度、重复身份及无法安全处理内容均拒绝。
- `validate` 检查 SQL 快照/清单摘要、每个文档的切片覆盖、集合 schema/index/load 状态、实际查询可见的全部切片身份和元信息及向量数量、维度、有限值。迭代读取必须关闭迭代器；不靠 count 或一次成功 load 推断完整可用。记录验证报告摘要，超时拒绝 ready。
- 保持 Milvus 2.4.13 / PyMilvus 2.4.15；完整读取使用该版本的迭代接口，具体一致性和就绪等待由真实依赖验收确认。BM25 从 SQL 版本快照完整读取，不再用 all_chunks 的默认限额构建。
- 构建与验证阶段不持有发布事务。发布前再次确认目标 ready、清单/配置兼容及集合仍可访问；外部校验后发生服务故障仍可能使请求失败，不能声称 SQL 发布事务保证 Milvus 始终健康。
- 指针初始化为空版本、代次 0。`publish` 在短事务内校验预期代次、切换目标版本、代次加一并写发布记录；条件不匹配拒绝，原值不变。`rollback` 使用同一机制，但目标必须曾成功发布且仍 ready/兼容。
- 每次发布/回退有独立 UUID `publication_id` 和内容摘要。重复标识、相同参数返回原发布记录，不再次切换；同标识参数不同拒绝。数据库提交异常后以新连接查原发布 ID；仍不可达时返回“结果未知”及查询标识，禁止报告失败后自动新建一次切换。
- 发布记录保存 publication_id、动作、目标版本、预期与实际前后代次/版本、UTC 时间及必填操作者声明。CLI 声明仅用于追溯，不冒充认证身份；执行权限依赖现有主机/数据库凭证边界，不引入管理 HTTP API。

### 轮次、缓存和 worker

- AI 聊天接收事务读取当前指针并与操作持久化 `knowledge_version`；以短锁定读取同发布事务建立先后关系，提交后释放，不贯穿模型调用。没有生效版本时，新的 AI 轮次在用户消息与操作提交前以服务不可用拒绝；人工模式不要求新建知识绑定。
- 同 UUID 的状态查询/重试先检查已有操作，恢复其原版本，不读新指针覆盖；已成功结果直接复用。版本不参与客户端内容指纹，发布本身不制造内容冲突。
- 版本传入所有可能调用 RAG 的专业 Agent、向量/BM25、草稿、最终结果和缓存补偿任务。历史消息仍按原会话事实读取；单轮固定版本不等于改写历史回答或把历史上下文都视为同版证据。
- Redis 答案键包含租户、knowledge_version 和 embedding 指纹；去重标记保持既有任务身份和生命周期，不单独增加 TTL。迟到任务写其原版本命名空间，不能污染当前答案缓存。
- 不带版本的旧答案缓存不读入新版；路由缓存仍只缓存路由结果，不用清全库解决知识一致性。
- 每个 worker 按版本构建不可变 BM25，合并同版冷启动，请求持有索引对象引用；内存缓存可淘汰无人使用的对象，不能删除 SQL 快照或改变旧请求持有的对象。单轮不因发布重启 worker 或切换索引对象。
- 版本不存在、集合不完整或 embedding 配置不兼容时记录固定技术失败，沿用现有降级/转人工结果及最终提交协调；不得改用新版、旧版或源文件拼成成功答案。

### 文档、引用及命令

| 接口 | 推荐契约 |
| --- | --- |
| `GET /api/docs?knowledge_version=...` | 省略则解析当前版本，返回列表及实际 knowledge_version；只列 ready 且曾发布的版本内容 |
| `GET /api/docs/{doc_id}?knowledge_version=...` | 返回该版脱敏正文、元信息及切片定位信息；不存在为 404，参数非法为 422；无当前版本为 503，不静默回退 |
| 引用与结果 | 引用保留旧字段，新增 doc_id/chunk_id，version 为本版 ID；结果和消息元信息增加 knowledge_version；前端显示版本并打开对应历史正文及切片 |
| `python -m scripts.knowledge build` | 从配置知识目录生成新版本，输出版本 ID；不发布 |
| `python -m scripts.knowledge validate <version>` | 验证本版清单、配置和真实向量制品，成功标记 ready |
| `python -m scripts.knowledge publish <version> --expected-generation N --operator NAME --publication-id UUID` | 显式发布；首次发布使用代次 0；内容冲突或并发代次不符时非零退出 |
| `python -m scripts.knowledge rollback <version> --expected-generation N --operator NAME --publication-id UUID` | 切回已发布且兼容版本，新请求使用回退目标，旧请求仍按原绑定完成 |
| `python -m scripts.knowledge list` / `show <version>` / `show --publication-id UUID` | 查询当前指针/代次、各版状态或原发布结果；不输出凭证及原始敏感内容 |

文档页由列表取得实际版本，之后详情请求使用同版。旧消息没有可验证版本时标记“历史未版本化”，不把原固定字符串 v1 推断为新快照 ID；现有标题和章节仍可展示，但不能声称链接能还原历史正文。

### 首次迁移与运行边界

新增增量 revision，保留 0001/0002。旧操作/任务的 knowledge_version 可空但标明遗留，禁止运行时偷偷绑定当前新版。首次接入停止旧写入和 worker，备份并盘点旧在途操作及缓存任务；按原契约完成或显式处置后，升级、校验、构建/验证并显式发布首版，再启动新版。已提交结果仍可查询，不删除历史、不新 UUID 自动重放。旧向量集合保留，源文件与旧答案不被当作历史快照补写。

安全 setup 不构建或发布知识；原 ingest 改为仅构建，演示装载在其显式确认范围内顺序调用构建、验证、发布并传入预期代次。首次切换后的在线发布和回退不再依赖重启 worker。

## 后果

### 正面后果

推荐方案使失败构建、在途请求和任务重放具有明确版本边界，历史引用可定位，发布结果可从 SQL 查询。上述均为预期能力，尚未实现验收。

### 负面后果与接受的取舍

文档/切片在 SQL 与 Milvus 重复存储；历史集合与快照不自动删除，容量持续增长。worker 冷启动及多版本 BM25 增加内存和首次访问成本。每轮新增指针读取，首次接入有维护窗口，CLI 发布仍需运维权限管理。SQL 事务不提供跨存储可用性或外部模型工件不变保证。

### 缓解措施与遗留问题

完整清单验证、短事务发布、任务显式版本和 [ADR-0009](0009-bounded-retrieval-execution.md) 控制故障与资源边界。历史保留容量纳入 ARCH-016，必须联合引用寿命、回退窗口、请求/任务重放年龄设计，首批不以删除标记或旧集合提前解决。

## 验证与重新评估条件

按 [首批验收矩阵](../architecture/evolution-roadmap.md#第一阶段验收矩阵)执行：构建和发布各阶段故障、SQL 提交后异常、两进程发布竞争、原 UUID/草稿/延迟任务跨发布和回退、2001 切片尾部召回、重复正文来源、源文件修改、版本化浏览器引用、旧结构升级及合成秘密边界。真实 MySQL/Redis/Milvus 和 Chromium 取得报告前，不将 ARCH-007 标为 Resolved。

多租户私有知识、模型/向量空间迁移、历史删除、紧急撤销已发布内容、大规模 BM25 内存成本或外部构建服务引入时重新评估。当前“在途旧版可完成”不适用于未来紧急内容撤销需求，届时须新提案。
