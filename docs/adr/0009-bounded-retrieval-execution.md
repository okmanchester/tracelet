## 背景与问题

异步检索函数直接执行同步向量 SDK 和 BM25 工作；慢服务与冷索引可能占用事件循环。在线知识版本增加冷启动与多版本并存，不能仅将阻塞工作挪入无界提交队列，否则超时和取消后仍可能积累后台工作。

本提案定义检索执行边界、排队上限、预算传播和取消后的容量归属，属于长期执行模型选择。它不提供服务端业务取消，不改变 ADR-0007 的租期、执行代次、人工接管和最终提交检查。

## 决策驱动因素

轻量请求及续租应能继续调度；运行与等待均有上限；请求预算不能被层层重新计时延长；停止等待不得错误释放仍在执行的资源。继续复用现有依赖，先治理知识检索路径，同时为后续容量验证保留可观测证据。

## 替代方案与取舍

| 方案 | 如何解决问题 | 优点 | 成本、限制与风险 | 与驱动因素的关系 |
| --- | --- | --- | --- | --- |
| 保持同步调用，限制业务并发 | 依靠较小流量减少阻塞机会 | 改动少 | 一次慢调用仍影响轻量请求及续租，无法表达后台容量 | 仅适合作为暂时限制 |
| 每次直接 to_thread 或默认线程池提交 | 同步调用离开事件循环 | 接入成本低 | 线程数有限不代表待执行任务有界；调用方取消也不能终止已运行线程 | 不足以控制积压与取消后的容量 |
| 有界工作队列与专用线程执行器 | 限制运行/等待数量，统一预算和结果回收 | 复用同步 SDK，边界可确定性验证 | 需要生命周期、取消状态与指标；CPU/GIL 工作仍可能争用 | 推荐，作为首批检索执行边界 |
| 独立检索进程或服务 | 在进程边界隔离 CPU 与阻塞调用 | 更强隔离，可独立扩容和重启 | 增加通信、部署、制品与故障治理，不会自动解决版本一致性 | 若线程隔离经实测不足时重评 |

## 已决定方案

### 执行与排队

- 每个应用进程建立一个检索专用执行器，W 个工作线程，最多 Q 个等待条目。使用显式有界异步队列及 W 个调度协程，调度协程仅在上一同步调用实际结束后领取下一项；不把任意数量任务提前提交线程池。
- 提交入口只接受由应用封装的 Milvus 读取、BM25 构建/评分及必要的融合工作，不接受客户端传入的函数或任意代码。查询结果先保持执行内存，业务写入仍经过原提交层。
- 队列已满立即产生内部固定类型 `retrieval_overloaded`；排队预算耗尽为 `retrieval_deadline`；SDK 异常为固定技术失败。专业 Agent 沿现有结果分类保留部分成功或尝试转人工，不能当作知识无命中，也不在 HTTP 外层新造一套业务重试。
- SDK 客户端在工作线程内创建并复用，每线程独享，不未经验证跨线程共享当前 lru_cache 的客户端。客户端/集合初始化和加载也必须在执行边界内。CLI 构建/校验单独运行于运维进程，不占请求进程的队列。
- BM25 从 ADR-0008 的 SQL 版本快照构建。相同版本以共享构建任务合并冷启动；单个等待者取消不取消其他请求共享的构建。队列内构建至多一份；版本对象完整构建后发布为不可变对象，旧请求引用不被替换。
- 已构建版本的内存缓存按有限条目 LRU 管理，请求持有对象引用；淘汰缓存只影响下次重建，不删除知识事实。内存上限还须实测语料和多版本大小，条目数量不等于字节容量保证。

### 预算、取消与关闭

- 从现有轮次总预算计算单调时钟 deadline，传给排队、客户端初始化、集合读取、搜索与后续阶段；每一步只使用剩余时间。CLI 验证使用自己的显式预算，不借用聊天 300 秒。
- 推荐新增 `retrieval_workers`、`retrieval_queue_capacity`、`retrieval_bm25_cache_versions` 配置；W/Q 必须为正整数，BM25 缓存至少容纳一个版本。首批缓存候选上限为两个版本（当前及常用回退版），以淘汰后仍可重建验收；不是同时请求只能涉及两个版本。
- SDK 的 timeout 取请求剩余预算和现有工具超时预算的较小值；多次调用不能各自重新获得完整轮次预算。BM25 的 CPU 工作不能靠取消 Future 强行中止，完成后的过期结果必须丢弃。
- 排队期间取消或 deadline 到期的任务，取出时跳过，不再调用 SDK。运行中取消只分离等待者；调度协程继续跟踪实际线程调用，直到完成才释放运行容量，结果按请求代次/deadline 丢弃。
- 共享冷启动的等待者可能多于任务条目；版本构建任务本身有界，等待仍受原轮次预算约束，不能把共享等待者计为额外工作线程或获得新预算。
- 不以包装层 Future 的取消状态推断底层线程已经结束，不通过自动换 UUID 重试补偿超时。续租、最终资格及接管检查按原规则执行，迟到结果没有写入特权。
- 生命周期开始时创建队列/执行器，关闭时停止接受新任务，拒绝或取消尚未开始条目，按现有进程关闭预算等待已开始工作并关闭客户端。底层同步调用失控不能被 Python 线程安全强杀；超出关闭预算由进程管理层结束进程，不能宣称 graceful shutdown 已完整排空。

### 可观测性

记录运行/等待数量、队列上限、排队时长、执行时长、满载拒绝、排队过期、运行中放弃等待及迟到结果丢弃；分离 BM25 冷启动与向量调用。关联 operation_id、trace_id、knowledge_version 和固定阶段，不记录原查询、凭证或原始 SDK 错误。控制指标标签基数，不把每个操作 ID 作为指标维度。

### 隔离实验与初始配置

2026-10-20，在 tracelet conda 环境使用 Python 3.12.15、Windows 11（10.0.26200）、rank-bm25 0.2.2、NumPy 2.5.4，运行未导入应用配置的隔离原型。未连接 MySQL、Redis、Milvus、模型、HTTP，也未调用评估/压测业务入口。

方法：比较 W=1/2/4，分别取 Q=2/4/8。每组运行三轮，每轮 12 个合成任务，每任务包含 30 ms sleep 模拟同步 I/O，以及 2001 个、每个 32 token 的预分词切片的真实 BM25 冷构建和评分。固定 12 个客户端在队列满时短暂让出调度再提交，仅是实验驱动，不是业务重试策略。用 10 ms 定时协程记录额外调度延迟；另用 barrier 验证 W=1/Q=1 的满载拒绝、运行中取消仍占用容量、排队取消跳过及最终排空。

| W / Q | 12 任务完成时间中位数（秒） | 三轮最大采样调度延迟（毫秒） | 观测运行/排队上限 |
| --- | --- | --- | --- |
| 1 / 2 | 0.4492 | 20.946 | 1 / 2 |
| 2 / 4 | 0.2564 | 16.038 | 2 / 4 |
| 4 / 8 | 0.1728 | 22.350 | 4 / 8 |

四项机制断言均通过。预设筛选规则是“最大采样调度延迟不超过实验阈值 50 ms 的候选中，取完成时间中位数最小者”，因此推荐 **W=4、Q=8 作为实现和下一轮隔离验收的初始配置**。50 ms 仅为本次实验筛选阈值，不是产品 SLO；这些秒数不是业务延迟或 Milvus 性能，不用它们宣称系统吞吐提升或选择部署 worker 数量。

本机可定位材料：项目根目录 `.pytest_cache/evolution/20261020-bounded-executor/probe.py` 与 `report.json`，已被现有 .gitignore 排除。激活 tracelet 后可在根目录运行 `python -B .pytest_cache/evolution/20261020-bounded-executor/probe.py` 重复本机原型；材料不随 Git 分发，后续生产回归须按本文方法在正式测试中独立实现。原始结果以 report.json 为准，不把再次执行与本次数字混合。

## 后果

### 2026-10-20 真实依赖资源复核

| --- | --- | --- | --- | --- |
| 1 / 2 | 2.797 | 0.391 | 0.594 | 22 |

数据来自忽略目录 `.pytest_cache/pilot/tracelet-pilot-28bc36d99cce4944a048e11d6bec408e/knowledge-scale.json`，可通过 [验收入口](../../backend/scripts/pilot_fixture.py) 的 `knowledge_scale` 复核方法。P95 使用 24 个样本的排序分位值，事件循环以 10 ms ticker 采样。各组满载拒绝、过期、放弃和丢弃计数均为 0；本实验没有使队列饱和，不能据此宣称 Q=8 最优。

保留 W=4/Q=8 作为首批初值：该受控语料的每轮耗时支持此并发配置，单查询尾延迟不随线程数单调下降。队列上限、取消归属及轻量 ASGI 请求由确定性回归另行验证；真实 SDK 极端慢调用、内存/连接长期上限、成本和部署目标仍待第四阶段测量。本次证据不改变原决定与适用边界。

### 正面后果

推荐机制使工作提交与取消后的资源归属可解释，慢同步调用离开事件循环，知识冷启动不会无界提交；已有隔离原型验证有限的队列/取消行为。业务实现和真实依赖效果尚未验收。

### 负面后果与接受的取舍

过载会显式失败而非无限排队；线程与客户端按应用 worker 数量增长。CPU/GIL、分词和共享模型仍可能影响事件循环；取消不节省已开始同步调用的资源。线程局部客户端增加连接与关闭成本，执行器需要额外生命周期和异常回收逻辑。W/Q 只限制任务数量，不限制单个语料的内存/CPU 上限。

### 缓解措施与遗留问题

以确定性 barrier 测容量归属，以真实依赖 profile 校验配置。保留 SQL 最终提交防线和固定错误出口；控制索引缓存并测量内存。BGE 的 to_thread/内部锁、其他同步请求路径、完整服务端取消及真实部署容量仍分别归 ARCH-013/012 的后续范围，不能仅凭本首批关闭全部问题。

## 验证与重新评估条件

1. 替身/可控 barrier：SDK 与 BM25 慢调用、W/Q 上限、满载拒绝、队列过期、运行取消不释放容量、排队取消不启动、迟到结果丢弃、关闭不接收新工作。
2. 并发同版只构建一次；不同版互不覆盖；淘汰后正确重建，取消一个等待者不影响其他等待者，构建失败后能明确重试。
3. 轻量 HTTP 与续租仍能被调度；接管期间迟到 AI 不能提交。单元原型的定时协程不能替代这一真实应用验收。
4. 随机独立真实依赖、多进程、2001 切片及浏览器全链路，按路线零失败/错误/跳过且清理成功；超时与错误保持脱敏。
5. 若真实事件循环延迟、内存/连接上限、GIL 争用、关闭卡住或队列拒绝不能满足后续确认的运行目标，重新评估进程隔离、专用检索服务及资源配置；不能仅增加线程掩盖问题。
