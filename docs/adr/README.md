# 系统架构决策记录（ADR）

这里记录对 Tracelet 系统具有长期影响的重要架构选择及其理由，供后续开发追溯。开发流程和本库的管理规则在本文说明，不为“采用 ADR”创建 ADR。

编号 ADR 见下方索引；Proposed 仅为待讨论提案，不表示已经批准或实施。

## 什么时候需要 ADR

先判断是否存在影响系统长期演进的选择，例如：

- 系统或模块边界、职责分工及跨边界协作。
- 数据归属、事实来源、一致性、事务和幂等保证。
- 租户隔离、权限与敏感数据的信任边界。
- 公共 API、事件、消息或其他重要接口契约。
- 关键基础设施、存储、执行模型和具有显著回退成本的运行机制。

开发协作规范、文档管理方式、普通缺陷修复、局部重构、样式和参数调整不自动触发 ADR。开发或部署机制只有实际改变上述系统架构约束时才考虑记录。修改文件多、使用新工具、发现一个缺陷，都不能单独作为理由。

遇到边界不清的情况，先说明具体系统影响，再与用户确认是否需要 ADR；不为普通任务增加审批。提出修复建议也不等于已作出架构决策。

### 流程走查示例

| 请求或情境 | 应有行为 |
| --- | --- |
| 修正错误提示文案并补测试 | 按普通任务处理，不创建 ADR，也不要求架构审批 |
| 选择会话事实来源及缓存故障策略 | 核查证据、比较方案，起草 Proposed；不能自行写成 Accepted |
| 想在方案中宣称性能改善，但尚未测量 | 明确写未测量及待做的验证，不填写虚构结果 |
| 新方案拟替代现有 Accepted ADR | 新建 Proposed 并关联旧记录；明确批准新方案后才更新替代链 |

## 工作流程

1. 查看 [已知问题](../architecture/known-issues.md)和下方索引，查阅相关 Accepted ADR 及替代链，避免重复或冲突。
2. 核查当前代码、约束和资料，区分事实、推测与待验证内容。没有历史记录时不推断过去的动机或批准过程。
3. 使用 [唯一模板](template.md)创建 Proposed，解释一个具体系统决策。已有同一问题的 Proposed 时优先修订该记录。
4. 检查背景、真实替代方案、取舍、负面后果与验证方式，再把具体提案交用户决定。起草和讨论不授权实施重大架构变更。
5. 根据明确决定更新状态和批准依据，同步索引、替代关系及关联问题。实现后在问题清单补充代码和验收证据。

可显式使用项目 skill `$adr`；入口为 [SKILL.md](../../.agents/skills/adr/SKILL.md)。skill 引用本文和模板，不另存一套规范。

## 文件与内容约定

- 文件名为 `NNNN-kebab-case-title.md`，从 `0001` 递增，每篇记录一个决策。分配前检查工作区和 Git 历史中的已有编号；不复用已分配编号。发生编号冲突时，为尚未定稿的新记录重新编号并更新链接。
- 标题与正文默认中文，文件名使用简短英文短语。日期使用 `YYYY-MM-DD`；使用实际发生的日期，不预填批准日期。
- 元信息采用模板中的 Markdown 表格。新记录状态为 Proposed，决策人、决定日期和批准依据留空，不能把 AI 写成批准人。
- 必须解释背景、可验证事实、决策驱动因素、真实可行的替代方案、推荐或已选方案及理由、取舍、负面后果、验证方式和重新评估条件。
- 适用时比较维持现状；若没有其他可行方案，说明约束及被排除的方向，不编造备选项。负面后果须写具体成本或限制，不能只写收益或用“无”敷衍。
- Proposed 使用“推荐”，Accepted 才使用“已决定”。不将提案建议表述为当前系统已具备的保证。

## 事实与证据

- 代码事实附仓库相对路径链接、符号名和检查基准提交；行号可作提示，但不能作为唯一定位方式。历史代码可通过 `git show <commit>:<repository-relative-path>` 核查。
- 标明证据类型：源码确认、测试或 mock 复现、推测、待验证。mock 证明特定控制流，不等于真实数据库、模型或生产故障验证。
- 外部资料附原始来源链接及查阅日期。性能、成本和可靠性数据须有测量方法、环境与结果依据；未测量就明确写“未测量”。
- 当前代码只能证明当前实现，不能证明它曾被批准、为何选择它，或某个替代方案历史上已被否决。
- 文档、审批摘录和复现材料不得包含真实凭证或未经处理的敏感数据。

## 生命周期与决定权限

| 状态 | 含义 | 进入条件 |
| --- | --- | --- |
| Proposed | 待讨论的提案 | 新建或修订，尚未正式决定 |
| Accepted | 决策已获准 | 用户明确接受具体提案，记录决定人、日期与批准依据 |
| Rejected | 提案未获接受 | 用户明确否决具体提案，记录理由及依据 |
| Superseded | 原决策已被替代 | 用户批准替代提案，新 ADR 已 Accepted，双方记录替代关系 |
| Deprecated | 决策停止适用且无替代方案 | 用户明确决定停用，记录原因及依据 |

正常流转为 `Proposed → Accepted / Rejected`，以及 `Accepted → Superseded / Deprecated`。AI 可以调查、起草、修订 Proposed 和补充证据；所有正式状态变化均须基于用户明确决定，不能自行批准。

决定必须能对应具体编号及提案版本。批准依据填写可定位的聊天、评审或其他记录；至少记录日期、提案对应的提交或内容摘要以及用户原话。没有可用链接时如实记录摘录和定位信息，不伪造 URL。用户的“继续完善文档”或针对其他任务的许可不是批准。仅当已有决定明确覆盖同一具体提案内容时才直接登记，无须重复征求。

Accepted、Rejected、Superseded 和 Deprecated 记录保留历史，不删除或改写成另一项决定。Accepted 后的实质性改变须新增 Proposed ADR，不能回退状态后覆盖原方案；Rejected 或已失效的方案需要重提时也创建新记录并互链。允许勘误、补充注明日期的实施证据和维护生命周期信息，不借此改变原决策含义。

Accepted 表示选择获准，不表示已经实施或问题已解决。实施进度和验收证据在 [问题清单](../architecture/known-issues.md)维护；ADR 可以补充实施证据，但不增加 Implemented 状态。
